# 5. ORIGINAL PROJECT IDEA

The original idea was narrower:

> Build a system that detects fake internships and fake job opportunities, especially scams targeting Indian students and job seekers.

# 17. IMPORTANT ISSUE WITH THE INDIAN DATASET

The dataset is relatively small and contains repetitive/synthetic patterns.

This creates a major ML risk:

> A TF-IDF classifier may learn templates or wording patterns instead of genuinely generalizable scam characteristics.

Examples of possible template leakage include repeated structures such as:

```text
Job Posting:
```

or recurring scam phrases.

Therefore this dataset should not be treated as sufficient by itself.

It is useful as an Indian-domain component but should be combined with broader public datasets.

---

# 18. STRUCTURE OF THE INDIAN JSONL

The original records had a structure conceptually similar to:

```json
{
  "system": "You are a Fake Job Detection AI trained on Indian job postings...",
  "user": "Job Posting: ...",
  "assistant": "Classification: Fake/Real. Red Flags: ..."
}
```

Important preprocessing decision:

The model should **not** train on the assistant explanation.

The assistant field contains the expected classification/explanation and would create label leakage.

Therefore:

- prompt/system information is not model text
- assistant explanations are not model input
- actual job/message text is extracted
- original classification information is retained only as metadata where appropriate.

# 33. DATA LEAKAGE AUDIT

This project explicitly encountered data leakage concerns.

## Indian Dataset Template Leakage

Approximately:

```text
77.3%
```

of Indian job texts began with:

```text
Job Posting:
```

This could become a shortcut feature.

---

## Spam Triage Header Leakage

Approximately:

```text
100%
```

of spam/promotional records contained a shared header structure similar to:

```text
Content type: email, Subject: ..., Body: ...
```

This structure appeared across labels.

Therefore the model must not be allowed to rely on this formatting artifact as its primary signal.

---

## Phishing Corpus Routing Strings

Approximately:

```text
3.5%
```

of phishing corpus examples contained Enron routing strings.

These may represent dataset-source artifacts rather than meaningful phishing features.

---

## Assistant Explanation Leakage

Assistant-generated explanations from the Indian JSONL were explicitly excluded from model text.

Otherwise the model could effectively see:

```text
Classification: Fake
```

during training.

That would make evaluation invalid.

---

# 34. IMPORTANT SEMANTIC LABEL PROBLEM

One of the biggest conceptual problems discovered is that the binary target:

```text
Fake/Threat vs Real/Safe
```

bundles together very different phenomena.

For example:

```text
fake job scam
phishing
commercial spam
prompt injection
credential request
```

are not necessarily the same type of threat.

Therefore a single binary classifier should primarily be considered a:

> High-recall threat filter.

It should not be interpreted as a complete understanding of email intent.

This is more aligned with the product's actual purpose.

**Do not fabricate labels.**

# 41. FEATURE ENGINEERING

The intended feature architecture combines:

## A. Word-level TF-IDF

Captures:

- scam phrases
- recruitment language
- credential requests
- urgency
- payment terminology
- promotional language.

---

## B. Character-level TF-IDF

Useful for:

- obfuscated words
- unusual spelling
- domain-like strings
- URL fragments
- punctuation patterns
- brand spoofing.

Character features are particularly useful in cybersecurity text because attackers can modify spelling to evade word-level models.

- credential-request terms
- urgency terms
- phone numbers

- Telegram/WhatsApp references

# 43. WORD VS CHARACTER TF-IDF

Word TF-IDF captures semantic-ish lexical patterns.

Character TF-IDF captures:

- spelling variations
- partial words
- URLs
- obfuscation
- suspicious domains
- repeated character patterns.

Combining them creates a richer representation:

```text
Word TF-IDF
      +
Character TF-IDF
      +
Cyber Signals
      ↓
Combined Feature Representation
```

# 44. EMBEDDINGS

Embeddings are part of the project's NLP roadmap.

The purpose is to capture semantic similarity beyond exact word overlap.

Example:

```text
"Send the registration fee"
```

and

```text
"Please pay the enrollment amount"
```

may be semantically related even if their exact words differ.

The project should distinguish:

### TF-IDF

Sparse lexical representation.

### Static embeddings

Dense vector representations.

### Contextual embeddings

Representations whose meaning depends on context.

---

# 45. SEMANTIC SIMILARITY

Embedding-based semantic similarity can help identify messages that express similar intent despite different wording.

For example:

```text
"Pay ₹500 to confirm your internship."
```

and:

```text
"Submit the registration amount to secure your position."
```

may represent similar scam intent.

The project should not claim semantic similarity is sufficient by itself.

# 51. CLASS IMBALANCE

The project must explicitly analyze class imbalance.

Security classification has asymmetric consequences.

For example:

### False Positive

A legitimate interview email is marked as malicious.

This can cause:

- missed opportunities
- user distrust
- important email being hidden.

### False Negative

A scam/phishing email is marked safe.

This can cause:

- financial loss
- credential theft
- security compromise.

Therefore accuracy alone is insufficient.

# 53. FP/FN TRADE-OFF

The decision threshold is not just a mathematical parameter.

It represents product policy.

For example:

### High recall

Catch more scams.

But:

```text

```

### High precision

Reduce false alarms.

But:

```text
more scams may be missed.
```

The appropriate threshold depends on the intended operating mode.

For a security system, the threshold should be tied to the actual risk policy.

# 126. BINARY LABEL MAPPING HAS LIMITATIONS

The binary representation:

```text

```

is useful for a first-stage threat detector.

For example:

```text

phishing

```

could all map to `1`.

That makes the model easier to train but less informative.

This is why the eventual architecture should consider:

```text

+

```

rather than forcing everything into one binary model.

# 179. FUTURE IMPROVEMENT — HARD NEGATIVES

A very important improvement is collecting legitimate emails that look suspicious.

Examples:

- real recruiter emails containing urgency
- real job portals containing links
- legitimate interview emails
- legitimate financial notifications.

These are **hard negatives**.

Training with hard negatives can reduce false positives.

---

# 180. FUTURE IMPROVEMENT — HARD POSITIVES

Likewise, collect sophisticated scams that look professional.

These help prevent the model from learning simplistic rules such as:

```text
bad grammar = scam
```

because modern scams may be professionally written.

---

# 181. FUTURE IMPROVEMENT — HUMAN LABELING

Because some labels are ambiguous, expert/user review can improve label quality.

Potential annotation schema:

```text
Security:
Safe / Suspicious / Scam / Phishing

Type:
Job / Interview / Advertisement / General / etc.

Priority:
Critical / Important / Normal / Low
```

This would create a much cleaner supervised-learning dataset.

---

# 182. FUTURE IMPROVEMENT — HIERARCHICAL CLASSIFICATION

Instead of one huge multiclass model:

```text
Email
 ↓
Threat?
 ├── No
 │    ↓
 │  Priority
 │
 └── Yes
      ↓
      Threat Type
      ├── Phishing
      ├── Fake Job
      ├── Payment Scam
      └── Other
```

This may be easier to interpret and maintain.

---

# 183. FUTURE IMPROVEMENT — ENSEMBLE CALIBRATION

If several models are combined, the ensemble output should ideally be calibrated before being exposed as a risk probability.

---

# 184. FUTURE IMPROVEMENT — EXPLANATION LAYER

The system could display:

```text
Why was this flagged?
```

with:

- suspicious phrases
- URL indicators
- sender-domain mismatch
- payment signals
- model feature contributions.

This improves user trust.

---

# 185. FUTURE IMPROVEMENT — EXPLAINABLE NLP

For TF-IDF + linear models, feature coefficients can identify influential terms.

For tree models, feature importance/SHAP may be used.

For neural/transformer models, token-level attribution can be considered.

But explanations should always be presented as:

> evidence associated with the model's prediction

rather than proof of malicious intent.

---

# 186. FUTURE IMPROVEMENT — URL ANALYSIS

An advanced version could analyze:

- domain age
- suspicious TLD
- URL length
- redirects
- IP-based URLs
- domain similarity
- punycode
- shortened URLs.

These are powerful security features.

They are **not necessarily implemented currently**.

---

# 187. FUTURE IMPROVEMENT — DOMAIN SIMILARITY

Brand spoofing could use:

```text
company.com
```

vs:

```text
company-careers.xyz
```

or typo-squatting.

Methods could include:

- edit distance
- character similarity
- domain embeddings
- known-brand lists.

Again, future unless verified.

---

# 188. FUTURE IMPROVEMENT — ATTACHMENT ANALYSIS

Attachments can be analyzed separately for:

- file type
- executable extensions
- suspicious archives
- macros
- malicious documents.

The current project should not claim attachment malware detection unless implemented.

---

# 189. FUTURE IMPROVEMENT — OCR

Scammers can put malicious text into images.

OCR could convert:

```text
Image
 ↓
OCR
 ↓
Text
 ↓
ML classifier
```

This would extend the system beyond text-only messages.

That is more important than simply achieving a high benchmark score.
